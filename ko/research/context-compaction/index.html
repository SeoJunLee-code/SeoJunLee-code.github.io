컨텍스트 압축

압축이 Claude Code 사용량을 줄이는가

혼합 결과AI 보조 구현독립 검토 없음
연구 질문대화 컨텍스트를 압축하면 작업 품질을 해치지 않고 Claude Code 구독 사용량을 줄일 수 있는가?
혼합 결과입니다. 권고: 조건부 채택. 이번 과제 크기에서 일부러 압축해도 Sonnet·Opus 5.5의 비용은 줄지 않았고, 150K 토큰을 넘으면 이득이 난다는 사전등록 예측은 반증되었습니다. 100K 토큰을 넘으면 가격이 오르는 Haiku 5.5에서는 이득이 있었습니다. 더 큰 절감은 호출마다 함께 보내는 고정 컨텍스트를 줄이는 데서 나왔습니다.

무엇을 보고 실험했나

출발점은 NVIDIA의 논문 You Don't Need Long Context(Belcak 외, 2026년 11월)입니다. 이 논문은 에이전트의 컨텍스트를 자주 압축하면, 곧 기록을 짧은 요약으로 바꾸고 새 컨텍스트에서 이어 가면, 정확도를 지키면서 비용을 줄일 수 있다고 보고합니다. 다만 비용 수치는 실제 청구액이 아니라 모형입니다. GPU 처리량 측정과, 컨텍스트가 길수록 토큰 단가가 오른다는 가정 가격으로 계산했습니다. Anthropic의 Sonnet·Opus 5.5 가격은 컨텍스트 길이에 따라 오르지 않고 Claude Code는 프롬프트 캐시에 크게 기대기 때문에, 이 절감이 Claude Code 구독에도 그대로 옮겨 오는지는 알 수 없었습니다.

  • Belcak 외, You Don’t Need Long Context, arXiv:2611.05306 (NVIDIA): 검증 대상인 주장. 논문 스스로 한계 절에서 비용 수치를 추정치라고 적습니다
  • CliffCompaction, Nguyen 외, arXiv:2609.26779: 오픈 가중치 모델로 Terminal-Bench에서 자동 압축이 성능을 지키며 비용을 “최대 50%” 줄였다고 보고합니다. 가장 가까운 선행연구입니다. 논문의 존재와 50% 수치는 원문과 대조했고, 캐시 회계의 세부는 2차 검토에서 온 것이라 확인하지 못했습니다
  • TokenPilot, Xu 외, arXiv:2606.17016: 프롬프트 배치를 바꾸는 가지치기는 프리픽스 캐시를 깨뜨린다고 주장합니다(존재 확인)
  • Anthropic 프롬프트 캐시 문서: Opus·Sonnet 5.5의 캐시 읽기는 입력 가격의 0.05배, 1시간 캐시 쓰기는 2배이고, 시험한 세 모델 중 100K 토큰을 넘으면 가격이 오르는 것은 Haiku 5.5뿐입니다
  • Claude Code의 프롬프트 캐시·비용 문서: /compact, /clear, 캐시 수명이 어떻게 동작하는지, 그리고 /usage가 요금제 사용량을 보여 준다는 점

질문

컨텍스트를 압축하면 작업 품질을 해치지 않고 Claude Code 구독 사용량이 줄어드는가? 줄어든다면 어떤 모델에서, 어느 컨텍스트 크기에서, 어떤 압축 방식으로 그런가?

방법

  • 헤드리스 Claude Code 하네스가 작고 결정론적인 저장소에서 미리 짠 여러 턴 대화를 돌리고 답을 자동 채점합니다
  • 긴 과제: T3(9턴, 검사 17개)와 T5(11턴, 검사 18개)는 코딩 과제, T4(8턴, 검사 15개)는 연구 분석 과제입니다. 대화 중간에 바뀌는 사실과 규칙, 묻혀 있는 요구사항, 마지막에 떠올려야 하는 정확한 숫자가 들어 있습니다
  • 모델: Claude Opus 5.5, Sonnet 5.5, Haiku 5.5. Sonnet은 모든 조건을, Opus와 Haiku는 G0과 G5를 돌렸습니다
  • 채점된 실행 83회: 파일럿 20회(반복 1회, 방향만 봄), 3단계 54회, 4단계 9회. 본 단계는 셀마다 3회 반복했습니다. 전체 API 환산 비용은 약 $71.6입니다
  • 성공 기준은 실행 전에 적었습니다. 어떤 방식이 더 낫다고 하려면 비용을 20% 이상 줄이고, 점수는 5점 넘게 잃지 않으며, 핵심 제약 검사에서 하나도 틀리지 않아야 합니다
  • 사용량: 배치 전후에 /usage로 요금제 사용량을 읽었습니다. 단위가 1%p라서 실행 하나는 눈금보다 작고, 연구 전체가 주간 한도의 몇 퍼센트를 썼습니다. 그래서 조건별 비교는 Claude Code가 세션마다 남기는, 캐시를 반영한 API 환산 비용으로 했습니다. 이것은 요금제 사용량이 아니라 대리 지표이며, 전체 사용량은 이 비용과 대략 비례해 움직였습니다
  • 하네스 버그 하나를 찾아 고쳤습니다. 호출별 비용 필드는 누적값이라 세션을 이어 갈 때 이중으로 더해졌습니다

절감이 옮겨 오지 않는 이유 판단

  • 캐시 쓰기가 대부분입니다. Claude Code에서는 새 토큰마다 입력 가격의 2배로 캐시에 한 번 쓰고, 지난 기록은 0.05배로 다시 읽습니다. 실행 비용을 맞춰 보면 캐시 쓰기가 비용의 약 60~65%, 읽기가 약 20%, 출력이 15~20%입니다(Sonnet·Opus). 압축은 읽기만 줄이므로 절감 상한은 읽기 몫인 약 20% 근처이고, 거기에 요약을 쓰는 호출, 늘어난 출력, 프리픽스 재작성이 더해집니다. T5에서 읽기는 32% 줄었지만(3.7M → 2.5M 토큰) 비용은 1~2%만 줄었습니다
  • 가격이 컨텍스트 길이와 무관합니다. NVIDIA의 절감은 컨텍스트가 길수록 오르는 모형 가격에서 나옵니다. Sonnet·Opus 5.5는 가격이 일정합니다. 예외는 Haiku 5.5로, 100K 토큰을 넘으면 가격이 5배가 됩니다. 그 선 아래에 머문 덕분에 247K 과제에서 G5가 0.33배였습니다
  • 고정 오버헤드는 호출마다 냅니다. 저자의 실제 CLI 설정은 첫 호출을 7.7K에서 31.6K 토큰으로 늘렸고, 점수는 같은데 비용은 줄인 설정의 1.66~1.93배였습니다. 연구 중에 쓴 대화형 세션은 호출마다 약 117K 토큰으로 시작했고, 그중 62K가 MCP 도구 정의였습니다

정보 손실과 실패 실측

  • G1, G5, GN에서 한두 번의 압축으로 생긴 손실은 보이지 않았습니다. 바뀐 사실(포트 54329 → 54417, 상한 37.5% → 35%), 고친 제외 규칙, 묻힌 요구사항, 정확한 숫자까지 포함합니다. 단서: 대부분의 실행이 만점이었고, 압축은 최대 두 번이었으며, 과제는 합성입니다
  • 행동 하나마다 압축(G3)은 2회 중 1회에서 어떤 설계를 기각한 이유를 잃었고, 비용은 전체 기록의 4~7배였습니다
  • Haiku 5.5는 압축 여부와 상관없이 같은 기능 검사에서 실패했습니다. 컨텍스트 효과가 아니라 능력의 한계입니다
  • 채점기 버그 하나를 찾아 고쳤습니다. “9개” 같은 한국어 답이 단어 경계 기반 숫자 매칭을 깨뜨렸습니다

반증된 사전등록 예측 실측

3단계 결과는 전체 기록이 약 150K 토큰을 넘을 때만 압축이 이득이라고 시사했습니다. 4단계 전에 이를 예측으로 적었습니다. 더 긴 과제(T5, 최대 235K)에서 기준점 150K의 G5와 GN은 품질 손실 없이 G0의 0.8배 이하가 될 것이고, 둘 다 0.95배 이상이면 반증으로 본다는 것입니다. 결과: G5 0.99배, GN 0.98배였고 9회 모두 만점이었습니다. Sonnet 5.5에 대해 예측은 반증되었습니다.

권고: 조건부 채택 판단

  • 고정 오버헤드부터 줄입니다. 쓰지 않는 플러그인, MCP 서버, 스킬을 끄고 전역 지침을 짧게 둡니다. 실측: 같은 결과에 비용 40~48% 감소
  • Sonnet·Opus: 사용량을 아끼려고 작업 중간에 압축하지 않습니다. 이전 컨텍스트가 더 필요 없으면 작업이 자연스럽게 끊기는 지점에서 새 세션을 시작합니다(메커니즘에서 나온 결론이며 따로 시험하지는 않았습니다)
  • Haiku: 세션을 100K 토큰 아래로 유지하고, 작업이 이어지면 약 80K에서 구조화된 요약으로 압축합니다
  • 압축할 때는 구조화된 요약(규칙 원문, 정확한 값, 결정과 기각한 선택지, 파일 경로)을 쓰고 원본 기록을 다시 찾을 수 있게 둡니다. G5와 내장 /compact는 비용이 같습니다. 행동마다 압축하지는 않습니다
  • 일상 작업에서는 150K를 넘는, 하위 에이전트를 많이 쓰는 긴 세션을 피합니다. 저자의 사용량 내역에서 사용량 대부분이 그런 세션에서 나왔습니다

한계

  • 합성 과제만 썼고, 실제 작업에서는 검증하지 않았습니다
  • 셀마다 3회 반복이며 T4의 신뢰구간이 넓습니다. Opus T3의 0.76배는 구간이 1.01까지 걸쳐 있어 유의하지 않습니다
  • 요금제 사용량은 1%p 단위라서 조건별 결과는 API 환산 비용에 기댑니다. 구독 요금제가 캐시 토큰을 어떤 비중으로 세는지는 공개되어 있지 않고, 대략 비례하는 움직임은 비용 비례 계산과 맞을 뿐 그것을 증명하지는 않습니다
  • 기준점은 고정값이었고 실행마다 압축은 최대 두 번이라, 여러 번 압축할 때 쌓이는 손실은 시험하지 않았습니다
  • Claude Code 버전 하나, 모델 세 개
  • 신규성은 제한적입니다. 캐시를 고려한 상한과 Haiku 가격 구간 효과는 쓸모 있는 실용적 발견이지만, CliffCompaction과 TokenPilot이 비슷한 영역을 다룹니다. 프로젝트 스스로의 평가는 연구 논문이 아니라 짧은 기술 노트감이라는 것입니다

검증과 AI 활용

표의 수치는 프로젝트 최종 보고서와 자동 생성된 3단계 분석 파일에서 옮겼고 둘은 일치합니다. 4단계 비율은 배치 결과 파일에서 다시 합산했습니다. 그 밖의 분석은 다시 돌리지 않았습니다. AI 보조 구현입니다. AI 에이전트(Claude Code)가 하네스를 만들고, 실험을 돌리고, 분석과 보고서를 썼으며, 저자는 질문을 정하고 사용량 예산을 승인하고 3단계 설계를 골랐습니다. 시험한 모델은 연구를 진행한 에이전트와 같은 계열입니다. 문헌 조사는 웹 기반이었고, 위에서 확인했다고 적은 출처만 원문과 대조했습니다. 코드와 원본 데이터는 비공개로 보관합니다. 독립적인 검토는 없습니다.
