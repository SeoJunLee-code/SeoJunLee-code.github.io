Algorithm Innovation

A cache-line approximate membership filter

Mixed ResultsAI-assisted implementationNo independent review
Research questionWith equal memory, can an insert-only filter that reads one cache line, with fingerprint length following block load, beat blocked Bloom and Prefix filter at a practical cost?
Mixed results. The filter beats blocked Bloom on false-positive rate at equal memory, but it is slower, its core mechanism was already published (TinySet, 2015), and a pre-registered phase-2 speed study met only one of six targets.

Question

An approximate membership filter answers “is this key in the set?” with some false positives. Blocked Bloom filters read one cache line per query. This study asks whether a filter that sizes each key's fingerprint by how full its block is, and truncates on overflow, can use one cache line and still give fewer false positives at the same memory.

Method

  • A C++17 header implementation of the filter (variant EPF-nc, frozen before the confirmatory runs). Every baseline is the author's own implementation, because downloading third-party code was not allowed
  • False-positive rate: 10 held-out seeds at n = 3,984,588 keys and 3 seeds at n = 31,876,710; 5×10⁷ negative queries per cell
  • Cost: instruction counts and a cache simulator (cachegrind, simulated 256 KB last-level cache), plus wall-clock time on a shared machine
  • Hypotheses H1, H1b, H2, H3, H4 and their pass limits were written in a plan before the confirmatory runs, according to the repository's plan and review documents. The clone available here has one commit, so commit order could not be checked

H2 — against the Prefix filternot testable: no reference implementation––
  • Wall-clock: negative queries take 3.14× the time of blocked Bloom, 1.70× Cuckoo and 1.81× the Prefix-style reimplementation (the report calls the filter slow). Instruction and miss counts are the deterministic metrics; milliseconds are noisy on a shared machine
  • Novelty is not achieved: the report states the core mechanism is TinySet (Einziger & Friedman, 2015/2017), found by a prior-art check after the work began, and the added improvements are standard techniques worth about 0.2 bits per key
  • A second study on query speed was started but is incomplete: its result file judged_run2.csv is empty (0 bytes) and there is no verdict, so nothing from it is reported here

Limitations

  • Only the author's own baselines were measured: the original TinySet, the Prefix filter, VQF and Morton filter were not. The Prefix-style filter is a reimplementation from memory
  • Speed was measured on one shared machine with independent query loops; the regime dominated by cache misses was not tested by wall-clock
  • The large-n runs have only 3 seeds, and the filter is insert-only
  • Paper bodies were not read for the prior-art check; it relied on the authors' source code and abstracts

Verification and AI use

The figures above were checked by hand against the repository's results file. The repository's review file, written by an AI reviewer agent, reports no blocking issue and accepts three listed concerns; no independent human review is recorded. The repository has no AI-use statement; its logs describe an orchestrator with sub-agent roles (scouts, prior-art check, baselines, reviewer). AI-assisted implementation. The repository has no licence file.

November 2026 update: phase-2 speed study Reported

A pre-registered speed phase set 6 targets and met 1: answers and memory stayed identical. With a prefetch hint, negative queries fell from 34 ns to 21.6 ns and positive queries from 46.6 ns to 24.6 ns. Against cuckoo, though, the best new path was 1.81 / 1.81 / 1.78× on negative queries (target ≤ 1.25×) and 3.59 / 3.38 / 3.40× on positive queries (target ≤ 1.5×), slower than the phase-1 path in a loop without hints. Measured on one machine; no independent review yet. Source: output/speed-report.md on an unmerged branch.
