Mixed results. The filter beats blocked Bloom on false-positive rate at equal memory and its core mechanism was already published (TinySet, 2015). A follow-up speed study, on an open pull request that is not merged yet, explained why the filter is slow and made queries faster, but missed five of its six pre-registered speed goals.

Background

An approximate membership filter answers “is this key in the set?” with some false positives. Blocked Bloom filters read one cache line per query. This study asks whether a filter that sizes each key's fingerprint by how full its block is, and truncates on overflow, can use one cache line and still give fewer false positives at the same memory.

Method

  • A C++17 header implementation of the filter (variant EPF-nc, frozen before the confirmatory runs). Every baseline is the author's own implementation, because downloading third-party code was not allowed
  • False-positive rate: 10 held-out seeds at n = 3,984,588 keys and 3 seeds at n = 31,876,710; 5×10⁷ negative queries per cell
  • Cost: instruction counts and a cache simulator (cachegrind, simulated 256 KB last-level cache), plus wall-clock time on a shared machine
  • Hypotheses H1, H1b, H2, H3, H4 and their pass limits were written in a plan before the confirmatory runs, according to the repository's plan and review documents. The clone available here has one commit, so commit order could not be checked

  • Wall-clock: negative queries take 3.14× the time of blocked Bloom, 1.70× Cuckoo and 1.81× the Prefix-style reimplementation (the report calls the filter slow). Instruction and miss counts are the deterministic metrics; milliseconds are noisy on a shared machine
  • Novelty is not achieved: the report states the core mechanism is TinySet (Einziger & Friedman, 2015/2017), found by a prior-art check after the work began, and the added improvements are standard techniques worth about 0.2 bits per key
  • The follow-up speed study (phase 2) is reported in its own section below

Phase 2 — why it is slow, and a faster query path Measured

A second, pre-registered study (plan written first; results on an open pull request, not merged) asked why the filter is slow although it causes about half the cache misses, and whether it can be sped up. It measures query speed only: insert speed was not re-measured. Setup: held-out seed, 6.3 MB filter at 3,984,588 keys, pinned to one core, three runs at different times, three loop types (independent, serial, and hinted with prefetching); no confidence intervals, only the range over the three runs.

  • Cause: cache misses are cheap only when queries overlap. The filter has about 0.98 branch mispredictions per query (Cuckoo and blocked Bloom: none) and a long computation after the fetch, so misses do not overlap; its instruction count is 118 against 70 for Cuckoo
  • Fix: with prefetching and a new query path, negative queries went from 33.8–35.4 to 21.5–21.7 ns and positive queries from 45.6–47.7 to 24.6 ns, with identical memory and false-positive counts. Mispredictions fell from 0.98 to 0.49. Without hints the new path is slower than the old one, and removing all branches made it worse
  • Goals: identical answers and memory were met. The other five were missed: negative query within 1.25× of Cuckoo (measured 1.81, 1.81, 1.78×), within 2× of blocked Bloom (measured 4.11, 3.96, 4.14×), positive query within 1.5× of Cuckoo (measured 3.59, 3.38, 3.4×), and the Prefix-style and misprediction goals
  • Size sweep (negative queries, hinted, filter time ÷ Cuckoo time; one run per size, exploratory): 2 MB 2.30×, 6 MB 1.68×, 50 MB 1.18×, 403 MB 0.87× (the filter is faster). So “slower” depends on the filter size and holds mainly when the filter fits in cache
  • The phase 1 conclusions are unchanged: the false-positive advantage is the same because the bits are the same, the core idea is TinySet, and insertion still costs more than Cuckoo

Limitations

  • Only the author's own baselines were measured: the original TinySet, the Prefix filter, VQF and Morton filter were not. The Prefix-style filter is a reimplementation from memory
  • Speed was measured on one shared machine with the author's own baselines; the phase 2 size sweep has one run per size, the hints need keys known in advance, and an independent review of phase 2 has not been done
  • The large-n runs have only 3 seeds, and the filter is insert-only
  • Paper bodies were not read for the prior-art check; it relied on the authors' source code and abstracts
